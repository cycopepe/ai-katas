How the chat code works

A walk through the streaming chat CLI. We follow one message from the moment you press Enter until the cost line appears. Reading time: about 10 minutes.

The five files

The code is small on purpose. The files are split in one way that matters: code that talks to the network is in chat.py, and code that needs no network is in chat_core.py. The tests can check the second kind without spending money.

FileWhat it does
chat.pyThe chat loop, the streaming call, and the commands. It prints to the screen.
chat_core.pyPrices, cost math, command parsing, error messages, and the costs.md row. No network.
system_prompt.mdThe text that makes the model act as a requirements analyst. You can edit it.
compare.pySends one fixed prompt to Haiku, Sonnet and Opus and prints the cost of each.
test_chat_core.pyNine tests for chat_core.py.

The one idea to understand first

The API has no memory. Each request is a new start. If you want the model to remember the first message, you must send the first message again, together with the reply and your new message.

So the program itself must keep the conversation. It does this in one list, Session.history. Every request sends the whole list. This is what the three requests of a short chat look like:

Request 1367 input tokens
system promptyou: idea
Request 2440 input tokens
system promptyou: ideaanalyst: questionyou: answer
Request 3526 input tokens
system promptyou: ideaanalyst: questionyou: answeranalyst: questionyou: answer

The token numbers come from my test chat. They grow with every turn, and you pay for them every time. The system prompt is not part of history. It is a separate parameter, so it is never mixed with the messages.

A useful result: you can change the model in the middle of a chat. The new model just receives the same list.

One turn, from Enter to the cost line

Here is the path in time. The numbered steps below match the arrows.

sequenceDiagram
  participant U as You
  participant M as main loop
  participant T as run_turn
  participant H as session.history
  participant A as Claude API
  U->>M: types a message
  M->>T: not a command, so call run_turn
  T->>H: append your message
  T->>A: stream(model, system, history)
  A-->>T: text arrives in small pieces
  T-->>U: print each piece at once
  A-->>T: final message with usage and stop_reason
  T->>H: append the reply
  T-->>U: print tokens and USD

  1. The loop reads a line

    The loop waits for input. A line that does not start with / is chat text. parse_command returns None for it, and the loop calls run_turn.

    chat.py · lines 133–143
    while True:
    try:
        line = input("\nyou> ").strip()
    except (EOFError, KeyboardInterrupt):
        print()
        break
    if not line:
        continue
    command = parse_command(line)
    if command is None:
        run_turn(client, session, line)

    Ctrl-D or Ctrl-C at the prompt leaves the loop. The finally block at the end of main still runs, so the costs are saved.

  2. Add your message to the history

    The first line of run_turn puts your text into the list, in the format the API expects: a role and a content.

    chat.py · line 42
    session.history.append({"role": "user", "content": user_text})

  3. Open the stream

    This is the real API call. Each parameter has one job:

    chat.py · lines 45–51
    with client.messages.stream(
    model=session.model,
    max_tokens=MAX_TOKENS,
    system=SYSTEM_PROMPT,
    messages=session.history,
    output_config={"effort": EFFORT},
) as stream:
    model
    Which model answers. /model changes this value in the session.
    max_tokens
    The longest reply allowed. It is 8000. The hidden thinking of the model counts inside this limit.
    system
    The persona, read once from system_prompt.md.
    messages
    The whole history. This is the "no memory" idea in one line.
    effort
    How much the model thinks. It is "medium" for all models, so the price comparison is fair.

    The with block closes the connection for you, even when an error happens.

  4. Print the text while it arrives

    Streaming means the API sends the reply in small pieces. The loop prints each piece at once, with flush=True so the terminal does not wait. Then get_final_message() gives the complete message, which has the token counts.

    chat.py · lines 52–54
    for text in stream.text_stream:
    print(text, end="", flush=True)
message = stream.get_final_message()

  5. If the request fails, undo the turn

    Two things can go wrong: you press Ctrl-C, or the API returns an error. In both cases the code removes your message from the history with pop(). Without this, the history would hold a question that has no answer.

    chat.py · lines 55–62
    except KeyboardInterrupt:
    session.history.pop()
    print("\n[interrupted: this turn was dropped]")
    return
except anthropic.APIError as exc:
    session.history.pop()
    print(f"\n[error] {describe_error(exc)}")
    return

    describe_error turns the SDK exception into one clear line. It checks the most specific class first. For example, a timeout is a kind of connection error, so it is tested before the general connection error.

    chat_core.py · lines 96–99
    if isinstance(exc, anthropic.APITimeoutError):
    return "The request took too long. Try again."
if isinstance(exc, anthropic.APIConnectionError):
    return "Cannot reach the API. Check your network."

  6. Count the tokens and the money

    The message has a usage field with the real token counts. session.record adds them to the total of that model and returns the cost of this turn. The cost is the tokens times the price per million tokens.

    chat.py · line 64  and  chat_core.py · lines 23–25
    usd = session.record(session.model, message.usage.input_tokens, message.usage.output_tokens)

def cost_usd(model, tokens_in, tokens_out):
    price_in, price_out = PRICES[model]
    return (tokens_in * price_in + tokens_out * price_out) / 1_000_000

    The totals are kept for each model. That is why a chat that uses two models can write one correct line to costs.md.

  7. Check why the model stopped, then keep the reply

    Always read stop_reason before you trust the content. Here there are three cases.

    chat.py · lines 65–75
    text = final_text(message)
if message.stop_reason == "refusal":
    session.history.pop()
    print("\n[the model refused this request: this turn was dropped]")
elif not text:
    session.history.pop()
    print("\n[the model returned no text: this turn was dropped]")
else:
    session.history.append({"role": "assistant", "content": text})
    if message.stop_reason == "max_tokens":
        print("\n[warning: the reply was cut because it hit the token limit]")
    • refusal: the model said no. We drop your message so the next try starts clean.
    • no text: nothing to show. We drop the turn too.
    • normal: we save only the text of the reply in the history. A cut reply (max_tokens) is kept, with a warning.

    final_text joins the text blocks and ignores other block types, such as thinking. This is also why the history holds plain text: a model switch cannot break on thinking blocks from another model.

  8. Print the cost line

    chat.py · lines 76–79
    print(
    f"\n[{short_name(session.model)} | in {message.usage.input_tokens} | "
    f"out {message.usage.output_tokens} | ${usd:.4f} | session ${session.session_usd():.4f}]"
)

    The turn is finished. The loop goes back to step 1.

  9. When you leave, write one line to costs.md

    The finally block of main calls save_costs. It builds one table row from the totals and appends it to the file. If you sent no message, nothing is written.

    chat.py · lines 114–118
    def save_costs(session):
    if not session.totals:
        return
    append_costs_row(COSTS_FILE, costs_row("01", "1A streaming chat CLI", session.totals))

The three commands that are not chat

/model
Changes session.model. It does not touch the history. Names like haiku are turned into full IDs by resolve_model.
/count text
Asks the API how many tokens the next request would have, without sending it. It builds a new list with session.history + [...], so your real history is not changed. It needs the text because the history ends with a reply, and a request should end with a user message.
/summary
Not special for the API. It is a normal turn with a fixed text: "Please write the requirements summary now". The system prompt tells the model what format to use.

Words in this code

Token
A piece of text, often a short word or part of a word. The API counts and charges by tokens.
Stateless
The server keeps nothing between requests. Your program keeps the state.
System prompt
Instructions for the model that come before the chat. They set the role and the rules.
Stream
Receiving the reply in pieces while the model writes, not all at the end.
Effort
A setting for how much the model thinks. Thinking tokens are charged as output tokens, and you cannot see them by default.
stop_reason
Why the reply ended: end_turn (finished), max_tokens (cut), refusal (declined).
Dataclass
A short way to write a class that only holds data. Session and Totals are dataclasses.

Try it yourself

Reading is not enough. Each experiment below is small. Make a guess first, then run it, then open the box.

1. Print what the API really receives

Do this: add import json at the top of chat.py, and this line just before the with block in run_turn:

print(json.dumps(session.history, indent=2))

Guess first: after three turns, how many items are in the list?

Answer: five before the third reply: your message, the reply, your message, the reply, your message. The system prompt does not appear, because it is a separate parameter.

2. Break the undo on purpose

Do this: comment out the session.history.pop() in the APIError branch. Run the chat with a bad key: ANTHROPIC_API_KEY=sk-ant-bad uv run python day01/chat.py. Send two messages, with the print from experiment 1 active.

Guess first: what does the history look like after the two failed messages?

Answer: it holds two user messages and no replies. With a good key, the model would read them as one confused turn. This is why the code removes a turn that failed. Put the line back after the test.

3. Change how much the model thinks

Do this: in chat.py, change EFFORT = "medium" to "low". Run uv run --env-file .env python day01/compare.py. The run adds a line to costs.md, which you can remove if you do not want it.

Guess first: which column changes, tokens in or tokens out? And for which model do you expect the biggest change?

Answer: I did not run this one, so I cannot give you the numbers. Compare with the table in the day 01 README. The input column should stay the same, because the prompt is the same.

4. Switch model in the middle of a chat

Do this: send two messages with Haiku. Then type /model opus, and use /count with a short text. Switch back with /model haiku and use /count with the same text.

Guess first: will the two counts be the same?

Answer: the history is identical, but the count is made by the chosen model, and models can count tokens in slightly different ways. Write down what you see. It is a real fact about these models, and good for your notes.

What this code does not do yet

Good to know before you build on it:

  • Lost cost on failures. If a stream breaks halfway, you may be charged for the tokens already made, but the code does not record them. The error path skips session.record.
  • No limit on the history. A very long chat sends everything every time. The cost grows and the context window can fill.
  • Network code is not tested. The nine tests cover chat_core.py. run_turn and run_count were checked by hand with a real chat.
  • Prices are copied, not read live. They come from a price table cached on 2026-10-06. Check them again before you trust the USD numbers later.
  • Hidden thinking. You pay for thinking tokens but do not see them, so output tokens can be much larger than the visible text.
